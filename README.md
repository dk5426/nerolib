# Nerolib

Nerolib is a library for AgileX Nero arms. It implements a minimal hardware interface layer and a joint controller. Nerolib is written purely in C++ (with Python bindings) with only a Pinocchio dependency for gravity compensation and Ruckig for trajectory generation.

It talks to the arm over SocketCAN directly — no ROS, no `nero_sdk`.

## Features

- [x] Simple interface with Nero without ROS and [nero_sdk]()
- [x] Joint stiffness controller implemented through the MIT control mode
- [x] Velocity, acceleration and jerk limits with [Ruckig]() on-the-go trajectory generation
- [x] Gravity compensation from URDF, including a lumped end-effector payload (Wuji hand)
- [x] Python bindings
- [x] Gripper control
- [x] Multi-firmware support (DEFAULT ≤ 1.10, V111 == 1.11, V112 ≥ 1.12)
- [x] Firmware query and per-joint driver diagnostics over CAN

## What's new in 1.1.0

Breaking-ish changes are marked ⚠ — none require code edits, but they change behaviour.

**Multi-firmware support.** AgileX changed the CAN protocol across firmware revisions. `ControllerConfig.firmware_version` now selects the wire format: the MIT-mode code (`0x04` vs `0x06`), the `t_ff` encoding (8-bit with per-joint scaling and a CRC vs 12-bit unscaled), and the `CPV` move mode on V112+. It defaults to `DEFAULT` (≤ 1.10), so existing code keeps working — but ⚠ **if your arm runs 1.11 or newer you must set this** or it will not respond correctly. `get_firmware_version()` replaces the stubbed `get_nero_firmware_version()` that always returned `"1.0.0"`.

**Wuji hand gravity compensation.** New `urdf/*_wuji.urdf` models carry the hand, mount and end-effector stand as a lumped rigid payload on `link7`, generated by `scripts/make_wuji_urdf.py`. See [Using gravity compensation with a Wuji hand](#using-gravity-compensation-with-a-wuji-hand).

**Ruckig jerk limit.** ⚠ New `ControllerConfig.joint_jerk_max` (default 400 rad/s³), and the constructor now rejects a non-finite or non-positive value. Previously `max_jerk` was left at `+infinity`, which Ruckig's `validate()` accepts but the third-order profile solver turns into NaN — the cause of intermittent `ErrorExecutionTimeCalculation` failures and dropped commands mid-motion. The default is tuned to preserve the old feel.

**Ruckig failure recovery.** A failed profile calculation no longer drops a control command or abandons the commanded target. The loop now holds at the measured pose *with* gravity compensation applied, keeps the target, re-anchors only the current state, and retries on the next tick — turning a one-tick numerical failure into a non-event instead of a visible hitch plus a backstep. Repeated failures are rate-limited in the log.

**Configurable homing.** `reset_to_home()` takes `timeout_sec`, `position_tolerance`, `velocity_tolerance` and `settle_time_sec`, all with defaults matching the previous hardcoded behaviour.

**Firmware query and arm diagnostics.** `NeroInterface` is now exposed to Python, along with `DriverStatus`, `GripperStatus` and the `ArmStatus` / `ArmController` / `EmergencyStop` enums. `query_firmware_version()` asks the arm what it actually runs over CAN `0x4AF` instead of guessing. Two new tools: `scripts/get_firmware.py` (read-only) and `scripts/nerolib_reset.py` (inspect driver flags, clear latched motor errors).

**Easier installation.** `install.sh` bootstraps Miniforge if needed, works on x86_64 and aarch64, supports `--yes` and `--env`, and verifies the install. See [Installation](#installation).

**Fixes.** Type stubs in `nerolib/__init__.pyi` now match the actual bindings (they previously declared a nonexistent `set_gripper`, omitted `firmware_version`, `home_position`, `gravity_comp_scale`, `set_mode`, and the gravity-compensation setters, and typed `start()` as returning `None` instead of `bool`). Added a `.gitignore` so build artifacts stay out of the repo.

## Installation

### Quick install (stock Ubuntu, x86_64 or aarch64)

From a clean machine with nothing but `curl`:

```bash
git clone https://github.com/dk5426/nerolib.git
cd nerolib
./install.sh
```

That is the whole thing. `install.sh` will:

1. find conda/mamba — or offer to bootstrap Miniforge into `$HOME/miniforge3` if you have neither, including picking up an install that exists but isn't on your `PATH`;
2. create or update the `nerolib` conda environment from `environment.yml`;
3. build the vendored Ruckig and install it into that environment's prefix;
4. `pip install -e .`;
5. verify that `import nerolib` actually works, and print the CAN setup steps.

It uses the environment's own `gcc`/`g++` rather than the system toolchain, so you do **not** need `build-essential` or a matching system Pinocchio. The compiler is resolved by pattern, so the same script works on x86_64 and aarch64 (Jetson, Raspberry Pi) without changes.

Useful flags:

```bash
./install.sh --yes            # never prompt; for CI or provisioning scripts
./install.sh --env myenv      # install into a differently named environment
./install.sh --help
```

If an environment is already active, the script installs into that one instead of creating `nerolib`.

### Manual install

If you would rather drive it yourself:

```bash
mamba env create -f environment.yml     # or: conda env create -f environment.yml
conda activate nerolib
# build + install the vendored Ruckig into the env prefix first, then:
pip install -e .
```

`uv sync` also works to create a venv and install the package. Both paths assume Ruckig is already installed where CMake can find it — that is the part `install.sh` does for you.

If your environment does not live at the default `$HOME/miniforge3/envs/nerolib`, set `NEROLIB_CONDA_ENV` to its prefix before building.

### Bring up the CAN interface

Nerolib does not configure the bus for you. Before connecting, the interface named in `ControllerConfig.interface_name` must be up at 1 Mbit/s:

```bash
sudo ip link set can0 up type can bitrate 1000000
ip -details link show can0        # confirm state UP
candump can0                      # optional: verify the arm is chattering
```

For a bimanual setup, give each arm a stable name (e.g. `can_left` / `can_right`) via udev rules so the ports do not swap between boots, and pass that name as `interface_name`.

### Building the C++ library only

If you only want the C++ side, or are developing against it:

```bash
mkdir -p build && cd build
cmake ..
make -j
```

This produces `libNeroController` plus the test and utility binaries (`test_nero_controller`, `test_gravity_compensation`, `verify_fk`, `emergency_stop`, …).

## Quickstart

> **Safety first.** `start()` power-cycles the motors: the arm **will fall** if it is not resting in a supported pose. `stop()` puts the arm in damping mode so it descends slowly, then waits for you to press Enter before cutting the motors. Keep a hand on the arm and the e-stop within reach the first few times.

```python
import time
from nerolib import NeroController, ControllerConfig, FirmwareVersion

config = ControllerConfig()
config.interface_name = "can0"
config.urdf_path = "urdf/nero_cone-e_left_fixed.urdf"  # required for gravity compensation
config.firmware_version = FirmwareVersion.V112          # match your arm's firmware
config.gravity_compensation = True

nero = NeroController(config)

if not nero.start():
    raise RuntimeError("nero controller could not be started")

try:
    # 7 joint values + a gripper position. All arrays are 7-DOF.
    nero.set_target(
        new_target_pos=[0.0] * 7,
        new_target_gripper_pos=0.0,
    )
    time.sleep(1.0)

    state = nero.get_current_state()
    print(state.pos, state.vel, state.torque)
finally:
    nero.stop()
```

Note that `new_target_gripper_pos` is **required**, and that every joint array is 7 elements long, not 6.

### Compliant / zero-gravity mode

Drop `kp` to zero and leave gravity compensation on, and the arm holds itself up while staying backdrivable by hand:

```python
from nerolib import Gain, ControlMode, MoveMode

nero.set_mode(ControlMode.CAN_COMMAND, MoveMode.MIT)
nero.enable_gravity_compensation(True)
nero.set_gain(Gain([0.0] * 7, [0.5] * 7))   # kp=0, light damping
```

Raise `kp` a little (say 5.0) for a spring-to-target feel, or back to ~10–15 for stiff position holding. If the arm sags, the usual cause is an under-modelled payload — see the gravity compensation section below — not the gains.

### Homing

```python
nero.reset_to_home(
    timeout_sec=20.0,
    position_tolerance=0.02,     # rad
    velocity_tolerance=0.05,     # rad/s
    settle_time_sec=0.5,
)
```

Homing succeeds when every joint sits inside `position_tolerance` of `home_position` and below `velocity_tolerance` for `settle_time_sec` continuously. If homing times out with the arm visibly close to home, the tolerance is fighting a steady-state droop — again, check the payload model before loosening the tolerance.

## ControllerConfig

| Field | Default | Meaning |
|---|---|---|
| `interface_name` | `"can0"` | SocketCAN interface the arm is on |
| `urdf_path` | `"../urdf/nero_description.urdf"` | URDF used for gravity compensation |
| `default_kp` | `10.0` ×7 | Position gain per joint |
| `default_kd` | `0.8` ×7 | Damping gain per joint (matches the pyAgxArm reference value) |
| `joint_vel_max` | `1.5` ×7 | rad/s |
| `joint_acc_max` | `2.0` ×7 | rad/s² |
| `joint_jerk_max` | `400.0` ×7 | rad/s³ — **must be finite and positive**, see below |
| `home_position` | `0.0` ×7 | Target pose for `reset_to_home()` |
| `over_current_cnt_max` | `20` | Consecutive over-current readings tolerated before faulting |
| `controller_freq_hz` | `250.0` | Control loop rate |
| `gravity_compensation` | `true` | Feed-forward gravity torque from the URDF |
| `gravity_comp_scale` | `1.0` | Scale on that torque; must be finite and non-negative |
| `gripper_on` | `false` | Enable the gripper channel |
| `firmware_version` | `DEFAULT` | See the firmware table below |

### About `joint_jerk_max`

Nerolib uses the jerk-limited Ruckig solver, whose `InputParameter::initialize()` leaves `max_jerk` at `+infinity`. Ruckig's own `validate()` accepts that (it only rejects NaN and negatives), and the third-order profile solver then produces NaN intermediates on whichever ticks land in certain branches — surfacing as intermittent `ErrorExecutionTimeCalculation` / `ErrorSynchronizationCalculation` and a command dropped mid-motion. The constructor now rejects a non-finite or non-positive jerk limit up front.

The default of 400 rad/s³ is `joint_acc_max / 0.005 s`, i.e. an acceleration ramp lasting about 1.25 ticks of the 250 Hz loop. That is as close to the old (infinite) feel as a well-conditioned solve gets, so the fix does not require retuning the arm. Lower it deliberately if you want visibly rounded motion starts.

## Gravity compensation and URDF selection

Gravity compensation is only as good as the URDF's mass model, so pick the URDF that matches what is actually bolted to the arm.

| URDF | Use when |
|---|---|
| `urdf/nero_cone-e_left_fixed.urdf` | Left arm, no hand |
| `urdf/right_arm_final.urdf` | Right arm, no hand |
| `urdf/nero_cone-e_left_fixed_wuji.urdf` | Left arm **with a Wuji hand** |
| `urdf/right_arm_final_wuji.urdf` | Right arm **with a Wuji hand** |

## Using gravity compensation with a Wuji hand

A Wuji hand adds roughly 0.7 kg about 14 cm out from `link7`. If the URDF does not know about it, that torque is uncompensated: the arm sags in compliant mode and homing never settles inside its position tolerance. The `*_wuji.urdf` files exist to model exactly that load.

### 1. Point the controller at the `_wuji` URDF

That is the whole integration — nothing else in the API changes.

```python
import time
from nerolib import NeroController, ControllerConfig, FirmwareVersion, Gain

IS_LEFT = True

config = ControllerConfig()
config.interface_name = "can_left" if IS_LEFT else "can_right"
config.urdf_path = (
    "urdf/nero_cone-e_left_fixed_wuji.urdf" if IS_LEFT
    else "urdf/right_arm_final_wuji.urdf"
)
config.firmware_version = FirmwareVersion.V112
config.gravity_compensation = True
config.gravity_comp_scale = 1.0

nero = NeroController(config)
if not nero.start():
    raise RuntimeError("nero controller could not be started")
```

Use an absolute path if you launch from anywhere other than the repo root — `urdf_path` is resolved relative to the working directory. A missing or unparseable URDF throws out of the `NeroController(config)` constructor rather than silently falling back to no compensation, and it does so **even when `gravity_compensation` is `False`**, because the solver is always built.

The URDF must also expose exactly 7 actuated joints, since that is what the controller sends to the arm. The payload is attached on a *fixed* joint precisely so it adds mass without adding a degree of freedom.

The left and right payloads are **not** mirror images of each other (their CoMs differ in z: −0.0179 m vs −0.0291 m), so do not substitute one URDF for the other on the opposite arm.

### 2. Check the model offline first

Before powering anything, confirm the URDF itself is sound:

```bash
python3 test/verify_wuji_gravcomp.py
```

This loads both URDFs into Pinocchio and cross-checks the payload's gravity torque against an independent Jacobian derivation over random poses. It touches no hardware and opens no CAN socket, so it is safe to run with the arms off. If this fails, do not bother testing on the arm.

### 3. Then check it on hardware

```bash
python3 test/test_left_compliant.py --dry-run   # confirm the settings
python3 test/test_left_compliant.py             # ⚠ powers the arm
```

The script holds the arm compliant, measures drift, and interprets the sign for you. Or do it by hand:

```python
nero.enable_gravity_compensation(True)
nero.set_gain(Gain([0.0] * 7, [0.5] * 7))   # kp = 0, light damping
time.sleep(10)                              # move it around by hand
```

What you should see:

| Behaviour | Meaning |
|---|---|
| Arm holds position wherever you leave it, moves easily by hand | Payload is modelled correctly |
| Arm sinks / drifts downward | Compensation too weak — hand mass under-modelled |
| Arm drifts upward or feels like it is pushing back | Compensation too strong — hand mass over-modelled |

Test with the elbow out and the hand well away from the body, where the payload's moment arm is largest and the error is most visible. `test/grav_comp_hold.py` does this interactively with live `kp` and scale tuning (it has machine-specific paths at the top to adjust).

### 4. If it sags, fix the mass — not the scale

The tempting fix is to raise `gravity_comp_scale`, but that scales the torque for the *whole arm*, including links that were already correct, so it overcompensates the proximal joints while chasing the distal error. Regenerate the URDF with the real hand mass instead:

```bash
python3 scripts/make_wuji_urdf.py                    # 0.58 kg, stock Wuji Hand (default)
python3 scripts/make_wuji_urdf.py --hand-mass 0.745  # Wuji Hand 2
python3 scripts/make_wuji_urdf.py --hand-mass 0.62   # stock hand + ~40 g of cable
```

This rewrites both `*_wuji.urdf` files in place from their no-hand base URDFs. It reads the base files, not the generated ones, so it is safe to re-run as many times as you like. Restart the controller afterwards — the URDF is read once at construction.

Weigh what is actually bolted on, cables included, and pass that. The default of 0.58 kg is the datasheet weight of a stock hand excluding cables; the MuJoCo model it was derived from says 0.476 kg, because MuJoCo infers mass from mesh volume at the default density and lands well under the real thing. Inertia is scaled with the mass (same geometry, higher density) while the CoM is left where it is — the right correction when the mesh shape is right but the density is too low.

Reserve `gravity_comp_scale` for deliberate global de-rating (e.g. 0.4 while tuning gains on a bench), not for compensating a wrong payload.

### What the generator actually does

The `*_wuji.urdf` files are **generated, not hand-edited** — a `<!-- generated by scripts/make_wuji_urdf.py -->` banner marks the block. Editing them directly means losing the change on the next regeneration; edit the constants in the script instead. It takes the corresponding no-hand URDF and:

1. corrects `joint7`'s `rpy` (see below), and
2. appends everything distal to `link7` — the stand_v2 end effector, the `wuji_nero_mount` and the hand with its fingers at `qpos0` — as one lumped rigid body on a fixed joint. Pinocchio absorbs that fixed joint into `link7` automatically, so it costs nothing at runtime.

At the default 0.58 kg the lumped payload is **0.710 kg** (0.130 kg of fixed hardware + the hand), with its CoM at `(-0.0066, 0.1429, -0.0179)` m in the `link7` frame for the left arm.

Because it is one rigid body, this models the hand **in a fixed finger pose**. Closing the fingers on a heavy object is not represented — for a grasped payload you would need to extend the model.

### Why `joint7`'s rpy differs between the base and `_wuji` URDFs

URDF `rpy` is extrinsic ZYX while MuJoCo `euler` is intrinsic xyz, and the two files were originally reconciled by copying the numbers across rather than converting them. The MJCF's `euler="1.5708 0 -1.5708"` is `rpy="-2.356194 1.570791 2.356194"` in URDF terms; the base URDFs carry the unconverted `rpy="±1.5708 0 -1.5708"`, which puts `joint7`'s axis perpendicular to the real wrist-roll axis.

That is harmless in the base URDFs because `link7` there is effectively massless (1 µg), so nothing distal is being placed. It stops being harmless the moment a hand hangs off `link7` — which is why the generator rewrites it.

## Firmware Version

AgileX has changed the Nero CAN protocol across firmware versions. Set `firmware_version` in `ControllerConfig` to match the firmware running on your arm:

| Constant | `software_version` reported by arm | MIT mode code | t_ff encoding |
|----------|------------------------------------|---------------|---------------|
| `FirmwareVersion.DEFAULT` | ≤ 1.10 | `0x04` | 8-bit, per-joint scaling, CRC |
| `FirmwareVersion.V111` | == 1.11 | `0x06` | 12-bit, ±16 Nm, no CRC |
| `FirmwareVersion.V112` | ≥ 1.12 | `0x06` | 12-bit, ±16 Nm, no CRC + CPV mode |

> **Firmware vs software version:** AgileX calls these *firmware* versions, but the arm self-reports the same number as `software_version` in its CAN status packet. The two terms refer to the same thing — use whatever is printed on the arm's controller box or returned by the AgileX configuration tool.

If `firmware_version` is not set it defaults to `FirmwareVersion.DEFAULT`, so existing code continues to work without changes.

### Ask the arm which firmware it runs

```bash
python3 scripts/get_firmware.py                    # can_left + can_right
python3 scripts/get_firmware.py can0
```

```
  [can_left]
    software_version : 1.12
    use              : FirmwareVersion.V112
    wire format      : MIT code 0x06, 12-bit t_ff over +/-16 Nm, no CRC, ...
```

This is read-only and safe on a powered, idle arm: it sends one request frame (CAN `0x4AF`, the same exchange pyAgxArm's `get_firmware()` uses) and reads the reply. It never enables motors, sets a mode, or commands motion.

In code:

```python
from nerolib import NeroInterface, FirmwareVersion

iface = NeroInterface("can0")                       # opens the bus, nothing else
version = iface.query_firmware_version()            # "1.12", or "" on timeout
fw = NeroInterface.firmware_version_from_string(version)   # FirmwareVersion.V112
```

`firmware_version_from_string` compares numerically, so `1.9 < 1.10 < 1.11` orders correctly rather than lexically. An unparseable string falls back to `DEFAULT` with a warning.

The version is also printed on the arm's controller box and available from the AgileX configuration tool.

### ⚠ Nerolib does not auto-detect this

Querying the arm and *configuring* the library are separate steps. `ControllerConfig.firmware_version` is what the library speaks; `get_firmware_version()` just echoes it back. Nothing cross-checks the two, so a wrong setting is not caught at startup — `query_firmware_version()` is how you find out, and you still have to set the config yourself. (The old `get_nero_firmware_version()` was a stub that always returned `"1.0.0"`; it has been removed.)

Set it once per arm, from the arm's actual reported version, and treat it as part of your machine configuration rather than something to guess. `scripts/nerolib_reset.py` warns when the version it is speaking disagrees with what the arm reports.

### What actually changes on the wire

All three versions share the same frame layout for the motor command (`0x15A + motor_id`) and the same encoding for position, velocity and gains. Only the mode code and the last two bytes differ.

**1. MIT mode code (frame `0x151`, byte 1).** `MoveMode::MIT` is translated on the way out and translated back on the way in, so `get_move_mode()` always reports `MoveMode::MIT` regardless of firmware:

| | Wire code for MIT |
|---|---|
| `DEFAULT` | `0x04` |
| `V111` / `V112` | `0x06` |

**2. `t_ff` encoding (bytes 6–7 of the motor command).**

`DEFAULT` packs an 8-bit torque plus a 4-bit CRC, and pre-scales torque per joint so every joint's range maps onto a common ±18 Nm encoded span (mirroring pyAgxArm):

| Joints | Input range | Scale | Encoded |
|---|---|---|---|
| 1–2 | ±24 Nm | ×0.75 | ±18 Nm, 8-bit |
| 3–4 | ±16 Nm | ×1.125 | ±18 Nm, 8-bit |
| 5–7 | ±8 Nm | ×2.25 | ±18 Nm, 8-bit |

The CRC is a 4-bit XOR of bytes 0–6, in the low nibble of byte 7.

`V111` / `V112` drop both the scaling and the CRC: a plain 12-bit torque over ±16 Nm for every joint, split across byte 6's low nibble and byte 7.

**This matters for gravity compensation.** The 12-bit field is far finer than the 8-bit one:

| | Torque resolution |
|---|---|
| `DEFAULT`, joints 1–2 | ≈ 188 mNm |
| `DEFAULT`, joints 3–4 | ≈ 125 mNm |
| `DEFAULT`, joints 5–7 | ≈ 63 mNm |
| `V111` / `V112`, all joints | ≈ 7.8 mNm |

On `DEFAULT` the shoulder quantises gravity torque in ~0.19 Nm steps, which is a visible source of coarseness in compliant mode. If your arm supports 1.11+, use it.

**3. `CPV` move mode** (`0x05`) exists only on `V112` and above. Selecting it on older firmware does nothing useful.

### Torque limits by firmware

- `DEFAULT`: ±24 Nm (joints 1–2), ±16 Nm (joints 3–4), ±8 Nm (joints 5–7)
- `V111` / `V112`: ±16 Nm all joints

Torques outside these ranges are clamped and logged, not dropped — partial torque is safer than none during gravity compensation. Note that `V111`/`V112` are **more** restrictive on the shoulder joints (±16 vs ±24 Nm), so a heavy payload that saturated nothing on `DEFAULT` can clip after a firmware upgrade. Watch the logs for clamp warnings.

### Symptoms of a wrong setting

Setting the wrong version is not a silent no-op, but it also does not announce itself clearly:

| Symptom | What happened |
|---|---|
| Arm never enters MIT mode; `set_joint_pos_vel_torque` logs "not in MIT mode" and returns | Mode code mismatch — the arm ignored the mode request |
| Arm holds position but feels dead / no gravity compensation | Torque bytes decoded as garbage by the other encoding |
| Arm twitches or jerks on every command | Same, with the garbage landing on nonzero values |

If anything looks wrong immediately after `start()`, check this before touching gains. `candump can0` and comparing byte 1 of the `0x151` frames against the table above will tell you within seconds.

## Nero Interface

Nero arms use CAN as their communication protocol. `nero_interface.h` defines the hardware interface with the robot:

- `reset_arm(NeroInterface &interface)` / `reset_gripper(NeroInterface &interface)`: Disables and enables arm/gripper until they are active again in a timeout loop. `NeroController.start` uses these.

- `enable_arm(NeroInterface &interface)` / `disable_arm(NeroInterface &interface)`: Used to enable/disable Nero actuators. Disable powers off the motors and the arm will fall down if not supported!!!

- `enable_gripper(NeroInterface &interface)` / `disable_gripper(NeroInterface &interface)`: Used to enable/disable the Nero gripper.

- `NeroInterface::set_emergency_stop(EmergencyStop es)`: Cancels the current command and puts the Nero actuators in a damping-only mode, which allows the arm to slowly drop.

- `NeroInterface::set_arm_mode(ControlMode ctrl_mode, MoveMode move_mode, uint8_t speed_rate, ArmController arm_controller)`: Nero supports two control modes: MIT mode for low-level PD control of the actuators, and Joint Control mode which runs a joint controller in the firmware. Since Nerolib implements its own compliant joint stiffness controller, it uses MIT mode. This call lets you change between modes. `MoveMode::MIT` is translated to the correct wire code for the configured firmware automatically.

- `NeroInterface::set_joint_pos_vel_torque(JointState &joint_state, Gain &gain)`: Sends motor commands to all the actuators. Requires that the actuators are enabled and in MIT mode. You can command:
    * `desired_pos`: rad
    * `desired_vel`: rad/s
    * `feedforward_torque`: Nm
    * `kp`
    * `kd`

    The control law is: `K_p * (desired_pos - current_pos) + K_d * (desired_vel - current_vel) + feedforward_torque`

- `NeroInterface::get_current_state()`: Gets the current `JointState` from the arm.
- `NeroInterface::get_driver_status(int motor_id)`: `DriverStatus` shows error status, overcurrent, and enabled/disabled for arm motors.
- `NeroInterface::get_arm_status()`: Check `ArmStatus` enum for possible states. Expected to be `NORMAL`.
- `NeroInterface::get_control_mode()`: Check `ControlMode` enum. Expected to be `STANDBY` or `CAN_COMMAND`.
- `NeroInterface::get_move_mode()`: Check `MoveMode` enum. Expected to be `MIT` in MIT mode or `JOINT` in joint control mode. `CPV` is available on firmware V112+.
- `NeroInterface::get_firmware_version()`: Returns the `FirmwareVersion` the interface was constructed with — i.e. which wire format it speaks, not what the arm reports.
- `NeroInterface::query_firmware_version(timeout_sec)`: Asks the arm what firmware it is actually running (CAN `0x4AF`). Returns e.g. `"1.12"`, or an empty string on timeout. Read-only.
- `NeroInterface::firmware_version_from_string(version)`: Static. Maps a reported version onto the `FirmwareVersion` constant to configure.
- `NeroInterface::is_arm_enabled()`
- `NeroInterface::is_gripper_enabled()`

## Utilities

Built into `build/` alongside the library:

- `emergency_stop` — put the arm into damping-only mode immediately.
- `resume_emergency_stop` — clear the emergency stop.
- `diag_raw_can` — dump and decode raw CAN traffic when the arm is not behaving.

Scripts in `scripts/`:

- `get_firmware.py` — ask each arm what firmware it runs (read-only, see [above](#ask-the-arm-which-firmware-it-runs)).
- `nerolib_reset.py` — inspect driver status and clear latched motor errors (see below).
- `make_wuji_urdf.py` — regenerate the Wuji-hand URDFs (see above).
- `scale_urdf_mass.py` — scale masses in a URDF.
- `extract_mjcf.py` — pull inertial data out of an MJCF model.

### Diagnosing and resetting an arm

`scripts/nerolib_reset.py` is the nerolib equivalent of a pyAgxArm reset script. Use it when an arm refuses to enable, reports a driver error, or comes up in a bad state after an e-stop.

**Inspect only — safe, never touches motor power:**

```bash
python3 scripts/nerolib_reset.py --status-only
python3 scripts/nerolib_reset.py --status-only --watch 10   # re-poll for 10 s
```

It reports firmware, arm status, control/move mode, and per-joint driver flags — enable state, error, low-voltage, motor and driver over-temperature, overcurrent, collision and stall — decoded from the `0x261`–`0x267` status frames:

```
    joint 1: ENABLED   raw=0x40  clean
    joint 2: disabled  raw=0x20  ERROR, motor-hot
    summary: 6/7 enabled, 1 in error
```

It also flags a firmware mismatch between what the script is speaking and what the arm reports.

**Reset — ⚠ this cuts motor power and brings it back:**

```bash
python3 scripts/nerolib_reset.py                 # prompts before doing anything
python3 scripts/nerolib_reset.py can0 --firmware V112
```

Disabling powers the motors off, so **an unsupported arm will fall**. Put it in a low, supported pose first. The script requires you to type `reset` at a prompt, and aborts before opening any interface otherwise. Motors are left **enabled and holding** at the end — support the arm before disabling it again or powering down.

The same operations are available from Python via `NeroInterface`, along with the blocking `reset_arm` / `enable_arm` / `disable_arm` helpers that retry until the arm reports the requested state:

```python
from nerolib import NeroInterface, reset_arm

iface = NeroInterface("can0")
print([iface.get_driver_status(i).driver_error_status for i in range(7)])
reset_arm(iface, timeout_sec=5.0)   # ⚠ powers motors down and back up
```

### Verifying a gravity-compensation setup

Two scripts in `test/`, meant to be run in this order.

**`verify_wuji_gravcomp.py` — offline, no hardware.** Loads the base and `_wuji` URDFs into Pinocchio and checks the payload three ways: that it adds mass without adding a degree of freedom (nq stays 7), that the mass and CoM recovered from the model match what the generator wrote, and — the real check — that the gravity-torque difference between the two models equals an independent derivation from the frame Jacobian, over hundreds of random poses. Safe to run with the arms powered off; it never opens a CAN socket.

```bash
python3 test/verify_wuji_gravcomp.py
python3 test/verify_wuji_gravcomp.py --poses 1000       # more thorough
```

**`test_left_compliant.py` — on hardware.** Puts one arm in compliant mode and measures how far it drifts while left alone, which is the number that tells you whether the payload mass is right. ⚠ This powers the arm; read the safety notes in the script header first.

```bash
python3 test/test_left_compliant.py --dry-run           # print the plan, touch nothing
python3 test/test_left_compliant.py                     # left arm, Wuji hand
python3 test/test_left_compliant.py --side right
python3 test/test_left_compliant.py --no-wuji           # bare arm
```

It reports per-joint drift and interprets the sign for you: sinking means the hand mass is under-modelled, rising means over-modelled.

Also in `test/`: `grav_comp_hold.py` (interactive live tuning of `kp` and scale), `grav_comp_sim.py`, `check_urdf_kinematics.py` and `tune_arm.py`. Note that several of these carry machine-specific absolute paths at the top that you will need to adjust.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Arm ignores commands after `start()` | Wrong `firmware_version` — MIT wire code mismatch |
| Arm sags under gravity compensation | Payload under-modelled; regenerate the `_wuji` URDF with the real hand mass, or check `gravity_comp_scale` |
| `reset_to_home()` times out near home | Same as above — steady-state droop keeps it outside `position_tolerance` |
| Intermittent Ruckig calculation errors | `joint_jerk_max` non-finite; the `NeroController` constructor now rejects this up front |
| `NeroController(...)` throws immediately | `urdf_path` missing or unparseable — it is resolved relative to the working directory, and is loaded even when `gravity_compensation` is `False` |
| No CAN traffic | Interface not up, or wrong bitrate — `sudo ip link set can0 up type can bitrate 1000000` |
| Build cannot find Ruckig | Run `./install.sh`, which builds and installs it into the conda prefix |
| `import nerolib` fails after install | Wrong environment active — `conda activate nerolib` |
| Not sure which `firmware_version` to set | `python3 scripts/get_firmware.py` asks the arm |
| Arm refuses to enable, or a joint reports an error | `python3 scripts/nerolib_reset.py --status-only` to see which joint and why, then drop `--status-only` to power-cycle the motors |
| CMake finds the wrong conda env / cannot find Boost | `NEROLIB_CONDA_ENV` unset or wrong — it defaults to `$HOME/miniforge3/envs/nerolib`. `install.sh` sets it for you |
